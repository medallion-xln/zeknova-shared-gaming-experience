# Durable staging server authority — ZGE-06

Start `npm run dev:staging-world`, then open `http://127.0.0.1:8796/examples/construction-world/?server=1`. Default data directory `/tmp/zge06-world`; use ZGE_STAGING_DIR for a fresh isolated directory and ZGE_STAGING_PORT for another loopback port. The CLI prints only the private fixture identity file path; copy the chosen fixture token into the staging login form. Alice/Bob/Carol are builders; Viewer is read-only; Outsider belongs to another world. Fixture sessions expire after 24 hours. These are disposable staging identities, not production accounts or a production identity service.

The launcher starts PHP with explicit `ZGE_STAGING_ENABLED=1` and `ZEKNOVA_ENV=zge-staging`, temporary database paths and a server-owned Node executable. Routes reject without both flags and loopback remote address. The static router allowlists example/source/vendor files and blocks production APIs, credentials, databases, setup/admin scripts and traversal. The new backend does not include production bootstrap/configuration, read .env values, apply production migrations or alter privileges. Its bearer identities are generated locally, stored hashed in SQLite and stored as raw fixture tokens only in a private mode-0600 file/browser session storage. Requests use Authorization rather than implicit cookies; client inventory/world snapshots/grants are rejected.

Observed existing backend: api/save.php and multiplayer.php use JSON files with flock, atomic temporary-file replacement for saves, per-player last-operation/revision and ID/health merges. No repository MySQL DDL/PDO database path or pre-existing SQLite workflow was located. PHP has PDO SQLite/MySQL drivers installed; availability is not schema/integration evidence. SQLite is the staging-only adapter. No MySQL or existing live PHP construction authority certification is claimed.

POST `/staging/world`: body worldId, optional command, cursor, replay and optional identity consistency check. Session hash lookup enforces expiry/world/role; forged playerId, cross-world access and viewer mutations reject. Allowed command fields are explicit for place/remove/move/select; catalog, terrain, collision, costs, resources, mission/reward rules and world revisions come only from trusted server state/content. The example has one shared builder/avatar and colony XP; this is not per-player character/profile replication.

PHP acquires BEGIN IMMEDIATE before reading state or dispatching. Durable receipt key `(world_id,player_id,command_id)` has a uniqueness constraint and canonical payload hash. Duplicate requests return the stored result; changed payloads conflict. It invokes the **existing** JavaScript ConstructionRuntime through a bounded local Node worker, with no tokens/production environment passed to gameplay. PHP owns the transaction and durable commit; JS owns gameplay policy. This avoids duplicating simulation rules in PHP. Worker startup (two calls in a normal command/sync response) adds measurable latency; it is a staging reference host, not a throughput-optimized service.

Within one SQLite transaction: validate current server revision; prepare candidate; insert unique event IDs/sequences and unique mission reward claim; CAS update snapshot/revision/cursor; insert accepted/rejected receipt and command; insert optional checkpoint and retain newest two derived checkpoints; COMMIT. synchronous=FULL and WAL are enabled. A valid rejected intent may persist its audit events/receipt but cannot change inventory/buildings/XP/gameplay revision. Invalid/unauthorized requests do not enter gameplay. No success acknowledgment is sent before COMMIT. A postcommit response loss is indeterminate to the client until a receipt lookup; it cannot justify a new logical ID.

SQLite serializes writers (including two separate PHP server processes in tests). CAS checks both gameplay revision and audit cursor, so rejection-only updates are not lost. Authenticated cursor pages return at most 128 events plus the current bounded runtime snapshot; client display history defaults to 256 records. Events/commands remain in durable archive indefinitely. Per-command payload max 64 KiB. Client timeouts preserve the exact pending request and expected revision in session storage; reconnection first reconciles and then resubmits. Old responses cannot rewind a newer confirmed cursor/view. Browser close preserves storage within that tab's session; this is not a cross-device outbox service.

Fault injection is disabled unless separately enabled with `ZGE_STAGING_FAULTS=1`; tests alone enable rollback, crash-before-COMMIT, crash-after-COMMIT and lose-ack headers. Real PHP process crashes and reopening the same SQLite file are tested. No fault option is part of normal production APIs.

Limits: loopback development server and fixture sessions; shared avatar/XP policy; synchronous Node subprocess cost; SQLite global write serialization; no MySQL certification, remote TLS/session provisioning, production rate/quota service or full legacy economic/utility/health/aid policy. Host-power-loss durability depends on OS/filesystem guarantees and is not certified by process-crash tests. `/tmp` storage survives these server/browser restarts, not machine cleanup/reboot retention. Production live API remains unchanged and uncertified for construction authority.
