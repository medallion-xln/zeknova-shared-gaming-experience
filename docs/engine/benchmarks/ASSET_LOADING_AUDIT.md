# Asset loading audit

**PASS_WITH_LIMITS for observed loads; historical GLTF stall root cause remains unresolved.** A dedicated fresh browser audit raised the ResourceTiming buffer to5,000 before navigation: 311 entries,53asset HTTPresponses,52distinctGLB paths and no repeatedGLB path in that bounded launch/attack interval. This supersedes the natural-run's truncated default250-entry resource table for duplication analysis; it does not certify every later campaign load.

The watchdog settled44GLTF loads, zero pending/failures/stalls; p50/p95/max load duration23/161/168.2ms in that audit. Natural-run final watchdog separately reported88completed loads, zero stalls/failures. Network resource durations, parser/watchdog duration and startup-ready events measure different things. The asset chart uses actual ResourceTiming durations with that label.

Player and ordinary enemy high-quality models appear in native screenshots; safe mode intentionally uses a simpler player. Buildings are visible after physical placement, and the Sunscar encounter executes models/projectiles/health. Only Sunscar's full encounter is browser-certified here; no assertion of all12bossmodel correctness. Independent cloned-animation behavior remains supported by existing asset tests, with no complete per-bone browser animation certification in this milestone.

Five observed workers remain live during the timed loop: four bounded asset workers plus adaptive runtime. Fetch cache is bounded64MiB; parsed cache is separately bounded64MiB, with expected eviction. The final parsed cache estimate is53.29MiB and fetch cache58.76MiB. These caches do not bound total renderer allocations. Original renderer total rose from84.72MiB to983.00MiB, with texture estimates rising72.34→752.17MiB; these are renderer-reported estimates, not measured resident VRAM. Later slopes are smaller; no retained-object leak conclusion follows.

Canonical model-runtime network identity in the new audit is `/assets/model-runtime-c96327ba.js`. The original game still warns about multiple Three instances because the legacy embedded renderer and vendor loader graph differ. This is a known ownership boundary, not newly caused by this verification. No minified runtime, model, transcoder, golden hash or gameplay loader was changed.

Failed-load fallback was observed through supported safe/unavailable paths and regression tests; deliberate GLTF corruption/worker-transcode-death during natural gameplay was not newly injected. Historical worker-pressure mitigation and previous stress results do not prove the original initialization hang's definitive cause.
