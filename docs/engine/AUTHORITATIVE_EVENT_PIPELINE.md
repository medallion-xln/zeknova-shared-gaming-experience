# Authoritative event pipeline — ZGE-05

`packages/core/src/GameplayEventJournal.js` exports the renderer-independent journal, factory and canonical JSON utility. `ConstructionRuntime` is the sole source-world producer. `zge.gameplay-event.v1` records are finite, deeply immutable plain JSON.

Fields: stable `id = JSON.stringify([worldId, transactionId, order])`, world/transaction IDs, contiguous global sequence, within-transaction order, gameplay revision, type, and explicit `{mode:'ENGINE',domain,owner,epoch}` authority. Payloads carry building, inventory/revision, mission detail, reward or rejection reason. Authority fields describe the producer; snapshots do not grant a writer lease. Version identifiers are not reused for incompatible formats.

Successful place order: ConstructionRequested → ConstructionCommitted → ResourcesChanged → BuildingCreated → MissionProgressChanged (objective, then completion and eligibility detail when relevant) → MissionRewardApplied when first eligible → WorldRevisionCommitted. Removal omits ResourcesChanged and emits BuildingRemoved. Grants emit ResourcesChanged. Selection/movement emit BuildingSelected/PlayerMoved. Rejection records Requested → Rejected at the unchanged world revision. Requested is an audit record published with the completed outcome, not a precommit callback.

The complete candidate (Construction, mission, player, reward IDs, revision, receipt and events) is validated and frozen before publication. The optional synchronous beforeCommit hook must be a pure validator. Exceptions discard the candidate. After publication, synchronous read-only subscribers receive ordered immutable records. A failed/mutating/reentrant subscriber is recorded in a bounded 100-entry diagnostic ring. It cannot invalidate the commit or request another runtime mutation while publication is in progress. Async subscribers are rejected/reported; external irreversible effects belong in a separate outbox with their own acknowledgment protocol.

Duplicate commands return their prior receipt and publish nothing. A changed payload using the same ID rejects. Journal append deduplicates identical records and rejects conflicting IDs, broken sequences/order, interleaved transactions, mixed worlds or decreasing revisions before replacing records. Restore validates journal/receipts/revision consistency and does **not** re-emit historical effects. A newly registered subscriber can explicitly request history; per-subscriber IDs suppress delivery repeats. Subscribers are cooperative code, not a JavaScript security sandbox.

Mission progress and the example XP reward are authoritative state transitions, not subscribers. Mission completion eligibility from the existing pure reducer is followed by a single explicit runtime-owned reward application, guarded by persisted reward IDs in the same transaction. Removal does not claw back historical achievement. Replaying events never reapplies rewards/charges. Deterministic replay runs saved commands from the same content/configuration and compares the entire state/journal.

Local event commit ≠ checkpoint acknowledgment ≠ network receipt. Server fixture responses identify checkpoint version/revision separately; lost replies leave the exact command in the client outbox. There is no globally exactly-once network delivery promise. GameplayEventJournal retains full history for these bounded fixtures; subscriber seen sets and checkpoint receipts grow with history. Checkpoint/delta compaction with retained idempotency fences remains required before long-running production use.

Tests: `source-runtime.test.mjs` covers ordering, immutable records, duplicate/conflict handling, replay, subscriber failure/reentry, reward uniqueness, malformed restore and cross-field receipt/revision validation. Browser inspector displays the same records used by the scene and persistence.
