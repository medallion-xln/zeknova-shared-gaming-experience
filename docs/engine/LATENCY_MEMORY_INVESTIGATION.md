# Latency and memory investigation — ZGE-10

ZGE-09's 600.15-second/3958-request measurement and final-source 180-second/1188-request follow-up are different samples and source lineages. The main run predates the authenticated early-rejection quota-accounting fix; the follow-up includes it. That fix does not change valid-command scheduling/commit semantics. Both used eight identities, eight gateways, one worker, six scheduled intents/second and extra measured construction preflight reads, synthetic initial 100,000 shared stone and unchanged 600/IP/240/principal minute quotas. Profiles and regression work could contend on the same host. Their preserved source captures remain in ZGE-09 evidence, rather than being relabeled.

The follow-up p99 of 463.28ms was reproduced with the original synchronous harness on current authority source: a new 180-second complete-service control is retained. The old harness runs synchronous `execFileSync(ps)` plus sequential `execFileSync(lsof)` for the full owned tree every five seconds on the same Node event loop that resolves HTTP response timing. This blocks delivery/reconciliation callbacks even when PHP has completed the request.

The old final-source trace's largest request took 505.38ms while PHP measured 12.59ms; the next took 498.62ms while PHP measured 7.03ms. Large gaps cluster at sampling boundaries. Among its 35 requests ≥100ms, median E2E-minus-handler time was 452.83ms. The new retained synchronous control has 1189 requests over 180.48s, p50/p95/p99 17.65/40.21/483.63ms and median unassigned slow-request gap 463.03ms. This supports benchmark event-loop blocking as the principal reproduced artifact; it does not turn every unobserved gap into a measured network/server stage.

`scripts/zge10-workloads.mjs` retains the workload and quotas but awaits asynchronous child processes for sampling and prevents overlapping samples. HTTP callbacks can run while `lsof` is collecting. Sampling duration, per-process RSS/CPU/FD, harness heap and private worker heap/GC telemetry are recorded. `scripts/zge10-analyze.mjs` preserves top requests with their actual PHP stages and runtime timing, per-PID resources and trend calculations. No gameplay admission/transaction optimization was made in response to a harness artifact.

Handler spans overlap and must not be summed. E2E-minus-handler remains unassigned listener/network/client scheduling time; socket accept timing is not independently measured. Remaining actual slow requests must be read alongside quota/admission/IPC/transaction spans and disclosed host contention. The sustained final values and top stage attribution are appended below after the complete run.

The earlier main-run RSS +6.97MiB and +6.44MiB/min tail are aggregate figures, including harness traces, launcher, eight Node gateway wrappers, PHP and worker. Per-PID differences show both positive and negative changes; the main run's largest positive process changes were +39.09/+26.86/+24.52MiB. Without historical heap/GC measurements these cannot be labeled a worker leak or assigned to a particular allocation source. The old final follow-up actually ended -59.69MiB aggregate, illustrating why an RSS endpoint is insufficient.

ZGE-10 adds cumulative observed GC count/duration and `process.memoryUsage()` after worker evaluation, exposed through existing authenticated private health. These are process-wide observations, not per-command GC causality. No forced GC or altered heap flags are used. Harness memory includes intentionally retained per-request trace/stage arrays and samples/progress JSON; DB growth retains receipts/events/claims. GC sawtooth, heap capacity/residency and caching differ from retained live heap. Bounded descriptors/workers are useful evidence, but a single local soak does not certify no leaks, arbitrary history retention or a production population/SLA.
